# Telegram-бот розіграшу iPhone 15 Pro

Готовий Telegram-бот на Python 3.12+, aiogram 3.x, SQLite/aiosqlite та FastAPI.

Увесь код бота знаходиться в одному файлі `bot.py`. Додаткових папок у GitHub-репозиторії не потрібно.

## Файли в корені

```text
bot.py
requirements.txt
.env.example
README.md
Dockerfile
render.yaml
```

## Що вміє бот

- Розіграш iPhone 15 Pro.
- 70 унікальних номерів квитків.
- Ціна одного квитка — 300 грн за замовчуванням.
- Перевірка підписки через Telegram `getChatMember`.
- Вибір декількох номерів через Inline Keyboard.
- Резервування номерів на 30 хвилин.
- Захист від подвійного продажу через транзакції SQLite + `BEGIN IMMEDIATE` + внутрішній lock одного процесу.
- Прийом фото квитанції.
- Адмін-підтвердження або відхилення оплати.
- Реферальна система: кожні 10 валідних запрошених користувачів дають 1 безкоштовний квиток.
- Профіль учасника та його квитки.
- Адмін-статистика, квитки, оплати, користувачі, реферали, розсилка, налаштування та визначення переможця.
- FastAPI `GET /` та `GET /health`.
- Long polling Telegram.
- Docker для Railway/Render.

## 1. Створити Telegram Bot

У Telegram відкрийте `@BotFather` → `/newbot` → створіть бота → скопіюйте токен.

## 2. Підготувати канал

Створіть або використайте канал для розіграшу.

Рекомендується додати бота адміністратором каналу з правом бачити учасників. Це потрібно для стабільної перевірки підписки через `getChatMember`.

`CHANNEL_ID` можна вказати як числовий ID на кшталт `-1001234567890`, а `CHANNEL_URL` — як посилання на канал, наприклад `https://t.me/your_channel`.

## 3. Заповнити Environment Variables

Скопіюйте `.env.example` для локального запуску або внесіть ці значення в Railway/Render:

```text
BOT_TOKEN=
ADMIN_IDS=123456789,987654321
CHANNEL_ID=-1001234567890
CHANNEL_URL=https://t.me/your_channel
CARD_NUMBER=0000 0000 0000 0000
SUPPORT_USERNAME=ua_101
COOPERATION_USERNAME=ua_101
TICKET_PRICE=300
TOTAL_TICKETS=70
REFERRALS_FOR_FREE_TICKET=10
RESERVATION_MINUTES=30
PORT=8080
DATABASE_PATH=/app/data/bot.db
LOG_LEVEL=INFO
```

`ADMIN_IDS` — Telegram ID адміністраторів через кому.

## 4. GitHub з телефона

Створіть новий repository.

Не створюйте жодних папок.

У корені repository створіть рівно ці 6 файлів:

```text
bot.py
requirements.txt
.env.example
README.md
Dockerfile
render.yaml
```

Вставте відповідний вміст з цього проєкту.

Не завантажуйте реальний `.env` та не записуйте токен бота в `bot.py`.

## 5. Railway

1. Створіть новий Railway Project.
2. Додайте service з GitHub repository.
3. Railway побачить `Dockerfile` у корені та використає його для збірки.
4. Додайте Environment Variables.
5. Для збереження SQLite після redeploy/restart додайте Railway Volume і змонтуйте його на `/app/data`.
6. Не масштабуйте цей SQLite-варіант на декілька інстансів.

Після деплою бот запускається командою з `Dockerfile` — `python bot.py`.

## 6. Render

У repository вже є `render.yaml`.

1. Створіть новий Blueprint/Web Service з GitHub repository.
2. Render використає `render.yaml`.
3. Задайте секретні Environment Variables, які мають `sync: false`.
4. Persistent disk уже описаний у `render.yaml` на `/app/data`.
5. Health check — `/health`.

Для SQLite використовуйте один інстанс. Не вмикайте autoscaling/кілька інстансів для цього варіанта.

## 7. Перевірка після запуску

Відкрийте публічний URL Render/Railway:

```text
/
/health
```

Обидва endpoint повинні повертати JSON зі статусом `ok`, коли процес і база готові.

Потім у Telegram відкрийте:

```text
/start
```

Для адмін-панелі:

```text
/admin
```

## Важливо про SQLite і масштабування

Цей проєкт спеціально зроблений під один запущений процес. SQLite зручний для простого запуску, але не є правильним вибором для горизонтального масштабування на декілька одночасних інстансів.

Для реального навантаження на декілька інстансів базу краще переносити на PostgreSQL, а для production polling використовувати лише один bot worker.

## Важливо про persistent storage

SQLite-файл повинен лежати на persistent storage. У цьому проєкті шлях за замовчуванням:

```text
/app/data/bot.db
```

На Render `render.yaml` уже містить persistent disk для `/app/data`.
На Railway створіть Volume та змонтуйте його на `/app/data`.

## Налаштування з адмін-панелі

Адмін може змінювати без перезапуску:

- картку/реквізити;
- URL каналу;
- username підтримки;
- username для співпраці;
- ціну квитка;
- правила;
- опис розіграшу.

Ці значення зберігаються в SQLite та мають пріоритет над початковими `.env` значеннями після першого запуску.

## Безпека

- Токен не зберігається в коді.
- Адмін-доступ обмежений `ADMIN_IDS`.
- Покупка перевіряє підписку.
- Один номер має тільки одного власника.
- Операції зміни статусу квитків виконуються під SQLite-транзакцією `BEGIN IMMEDIATE`.
- Дубльована реєстрація реферала блокується UNIQUE-обмеженням.
- Самореферали не зараховуються.
- Прострочені резерви очищуються фоновою задачею кожні 30 секунд.
- Критичні адмінські дії записуються в `admin_logs`.
- Кнопки мають простий in-process rate limit.

## Визначення переможця

Кнопка визначення переможця доступна після розподілу всіх 70 номерів.

Результат обирається серверним `secrets.choice()` серед усіх зайнятих номерів (`SOLD` та `FREE_GIFT`) і одразу записується в SQLite.

Після запису повторне натискання не генерує новий результат.

## Юридичний момент

Платні розіграші, лотереї та промоакції можуть мати окремі вимоги залежно від країни, механіки та умов участі. Перед фактичним запуском перевірте правила для тієї юрисдикції, де буде проводитися акція. Цей проєкт не є юридичною консультацією і не створює жодних юридичних гарантій.
